# TPN Labs

Company / brand: TPN Labs
About: TPN is a Bittensor subnet that makes large AI models small enough to run on constrained hardware, and proves they still work. We publish a specification — a memory ceiling and a quality floor — as an open competition. Independent teams worldwide compete to hit it, and the winning models are scored against benchmarks we generate ourselves and never publish, committed by hash before submissions open. Every result resolves to an exact model revision and a public run record. We also build TPN Bench, a benchmarking and quantization toolkit platform, and Gratis, which runs open models locally in a browser tab.
Audience: Three audiences, in rough order of volume. Developers and ML engineers who deploy open-weight models and care about memory, latency and whether quantization broke something. The Bittensor ecosystem — miners, validators, subnet watchers and TAO holders following competition results. And people running AI locally for privacy or cost reasons, who are more consumer than technical. Write for someone competent who doesn’t need jargon explained but will notice if you get a detail wrong.
Tone of voice: Plain and direct. State the fact and stop. Short sentences, concrete nouns, real numbers. Confident without selling — we show evidence rather than making claims. Never address the reader as “you” in announcements. No hype, no exclamation marks, no emoji beyond occasional sparing use. Technical where it earns the reader something, never technical as decoration. If something is uncertain or unresolved, say so plainly rather than smoothing over it.
Products and services (overview): TPN Subnet (Bittensor SN65) — open competitions that turn a hardware specification into a verified, compressed model. Released openly on Hugging Face.
TPN Bench (bench.trueperformancenetwork.com) — benchmark any model against sealed, uncontaminated test sets, compare it to its base model, and run quantization including importance-matrix and distillation methods. Free credits, then paid.
Gratis (gratis.trueperformancenetwork.com) — runs GGUF models locally in a browser tab or desktop app. No install, no account, nothing leaves the device.
Public results dashboard — stats.trueperformancenetwork.com
Words and phrases to use: compression, quantization, sealed benchmark, uncontaminated, committed by hash, memory ceiling, quality floor, open competition, verified, model revision, run record, constrained hardware, local, on-device, open weights, retention, base model, miners, validators, emissions, epoch
Words and phrases to avoid: Never use: “not just X, but Y” or any reversal of that shape. Three-item fragment lists for rhythm (“Faster. Smaller. Better.”). A colon used to set up a dramatic phrase. Em dashes used for drama. Sentences that tell the reader what matters (“and that’s the important part”, “here’s why this matters”, “this changes everything”).

Never use these words: revolutionary, game-changing, unlock, unleash, seamless, cutting-edge, leverage (as a verb), empower, robust, elevate, supercharge, transform, journey, landscape, ecosystem (except the Bittensor ecosystem specifically), delve, moreover, furthermore, “in today’s world”, “the future of”.

Never write in second person in announcements. Never claim a model is “better” without the number next to it. Never use “AI-powered” or “powered by AI”.
Legal and compliance rules: Never discuss token price, market cap, returns, or anything that reads as investment advice. Never predict emissions value or alpha token performance. Do not use “investment”, “profit”, “returns”, “guaranteed”, or “risk-free” in any context.

Every performance figure must come from the public dashboard and be reproducible there. Never round in our favour, never state a figure from memory, never compare against a base model without naming it. Do not state memory ceilings or emission splits unless confirmed in the competition specification.

Never claim or imply a competitor’s product is worse, and never name a competitor’s product in a comparison. Never present a roadmap item as shipped. Never claim a partnership, integration or customer that hasn’t been publicly announced by both sides.

Models produced in competitions are uncensored base models in some cases. Do not promote them on the basis of being uncensored or unrestricted

# TAO Performance Network (TPN)

TPN is a Bittensor subnet that incentivizes miners to build high-performance, quantized language models. Miners benchmark their own GGUF models, then submit the model plus the resulting benchmark run ids via a TimeLocked Commit scheme — hiding the submission until the scoring phase to prevent copying. Validators verify each run actually benchmarked the committed model, rank miners on those verified scores, and check the top candidates for RAM usage, file integrity and base-model provenance before distributing emissions. The subnet runs recurring competitions, each with defined benchmarks, scoring windows, and emission distributions.

## shared/validation/README.md
# GGUF Model Provenance Checker

Prescreen whether GGUF model B is plausibly derived from model A. Two static gates — no inference, no GPU. Stops early on hard disproof.

## Checks

**Check 1 — Tokenizer:** Compares tokenizer type, vocabulary, and BPE merge rules. Vocab size or merge count mismatch is a hard disproof. Entry differences <1% pass (common in fine-tunes that add chat-template tokens).

**Check 2 — Embedding CKA:** Samples `n_tokens` rows from `token_embd.weight` and computes linear Centered Kernel Alignment between A and B. CKA is invariant to rotation, permutation, and isotropic scaling, so it stays high under quantization/pruning and drops to the independent-model baseline otherwise. Pass if CKA ≥ threshold.

---

## Requirements

Python 3.11+ with:

```bash
pip install gguf numpy
```

---

## Run

```bash
python provenance_check.py model_a.gguf model_b.gguf
python provenance_check.py model_a.gguf model_b.gguf --threshold 0.85
python provenance_check.py model_a.gguf model_b.gguf --n-tokens 2048 --seed 123
```

**Flags:**

| Flag | Default | Description |
|------|---------|-------------|
| `--threshold` | `0.80` | CKA accept threshold — calibrate against known-independent same-tokenizer models |
| `--n-tokens` | `4096` | Token rows sampled for CKA |
| `--seed` | `42` | RNG seed for reproducible sampling |

Exit code `0` = plausible derivative, `1` = not a plausible derivative, `2` = input error.

---

## Interpreting results

| Result | Meaning |
|--------|---------|
| **PASS** (both checks) | B is a plausible derivative of A — confirm via benchmark |
| **FAIL** (tokenizer) | Hard disproof: different vocab/merges |
| **FAIL** (CKA) | Embedding geometry too different; not a plausible derivative |

The threshold MUST be calibrated: measure CKA for a few known-independent models that share the same tokenizer, then set the gate above that baseline.


---

## Limitations

- **Prescreen only.** A PASS is not confirmation — follow up with benchmarking.
- **Quantized tensors supported.** `_dequant_rows` dequantizes on the fly; requires `embed_dim % block_size == 0` (all valid GGUF files satisfy this).
- **Cannot detect weight replacement.** A model could share the tokenizer but have entirely retrained embeddings; Check 2 would catch this, but only if the CKA threshold is set correctly.
- **From-scratch / distilled models correctly fail.** They share no weights with A and will fall below the CKA threshold.
- **For high-stakes decisions**, follow up with dynamic checks: run both models on the same prompt distribution and compare output logits or KL-divergence.

# TPN Validator

Two validator modes, controlled by `VALIDATOR_MODE` (`.env`):

- **leader** (default) — scans chain reveals, verifies the benchmark run ids
  miners committed, ranks on those verified scores, prechecks the top candidates,
  computes and sets weights, persists every scoring run to SQLite, and serves a
  read-only HTTP API for followers and dashboards.
- **follower** — parses competitions itself but reads scoring results from a leader
  validator's API instead of verifying/prechecking. Recomputes emission weights
  locally from the leader's `ScoringResult`s and sets its own weights.

Both modes run the same chain-copy `weight_loop()` fallback in parallel — if a
follower can't reach its leader, it just skips that competition's cycle and keeps
submitting stake-weighted consensus weights from chain until the leader is reachable
again.

`python main.py --clean` wipes it before starting.

## Leader API

`GET /v1/follower/scoring-results?competition_id=X`
Final scoring results for one competition. This is what followers poll to set
weights. `competition_id` is required — 400 without it.

```json
{
  "results": [
    {"competition_id": "tpn-001", "hotkey": "5F...", "final_score": -812345,
     "max_memory_kb": 812345, "finalized_at": 1756100000.0}
  ],
  "scored_status": "scored"
}
```

`results` is empty until the competition reaches stage `finalized`, so followers
never see partial rankings. `scored_status` is `null` before scoring starts, then
one of `scored`, `failed_no_reveals`, `failed_no_participants`, or
`failed_stage1_infra`. An empty `results` with a `failed_*` status means the leader
gave up and no weights will ever be published for that competition.

`GET /v1/state/competitions/{competition_id}`
Full detail for a competition: revealed candidates with their status and failure
reasons, benchmark results, scoring results, and weights history. Superset of the
follower endpoints — dashboards should use this instead of stitching
`/v1/follower/*` calls together. 404 if no competition with that id exists.

`GET /v1/state/status`
Leader's task/loop status (same shape as `get_validator_status()`).

`GET /v1/state/weights-history?competition_id=X`
Past weight submissions for a competition.

`GET /v1/competitions`
All competitions. `?active=true&block=N` filters to active ones at block `N`
(current chain block if `block` omitted). This is what followers, the miner CLI,
and dashboards should read competition config from. 400 if `block` is not a
non-negative integer.

`GET /v1/competitions/{competition_id}`
Single competition spec. 404 if not found.

`POST /v1/competitions` (requires `Authorization: Bearer <ADMIN_API_KEY>`)
Create or update (upsert by `id`) one competition. Body is a full `CompetitionSpec`
JSON object — validated the same way as `competitions/*.json` was before this moved
off GitHub. 401 on missing/invalid token, 503 if `ADMIN_API_KEY` isn't set, 422 on a
spec that fails validation. 413 on a body over 256 KB.

`DELETE /v1/competitions/{competition_id}` (requires `Authorization: Bearer <ADMIN_API_KEY>`)
Remove one competition spec — intended for an id pushed by mistake, before anything
has been scored against it. 404 if not found, 401/503 on auth as above.

Refuses with 409 once the competition has scoring state (reveals, run verifications,
scoring results, weights, or a scoring stage), because those tables key off
`competition_id` with no foreign key — dropping the spec would leave their rows
unreachable but still present. Append `?force=true` to delete the spec anyway;
the scoring rows for that id are left in place.

`POST /v1/competitions/{competition_id}/reset-scoring` (requires `Authorization: Bearer <ADMIN_API_KEY>`)
Clear scoring state so the competition re-runs from stage 1. For a competition that
gave up on a transient failure — `failed_stage1_infra` (coordinator unreachable, chain
scan failed), `failed_no_reveals`, or `failed_no_participants` — while its scoring
window is still open. Without this the only recovery was `--clean`, which wipes every
competition's history plus the ban list.

Deletes that competition's `revealed_candidates`, `benchmark_results`,
`scoring_results`, and its `scored_competitions` row, and reports
the per-table counts. **Bans and weights history are preserved** — a ban records
proven miner misbehaviour that a validator-side infra failure does not undo, and
weights history stays as an audit trail of what was already set on chain.

**There is no override.** A reset is allowed only when both hold:

- The competition's stage is `stage1_ranking` (including a competition that has not
  been touched yet), `failed_no_reveals`, `failed_no_participants`, or
  `failed_stage1_infra`. A competition in `stage2_scoring` or `finalized` is refused
  with 409 — stage 2 is mid-run, and a finalized competition already had weights
  computed and published from its result.
- Its scoring window is still open (`current_block < scoring_end_block`). Refused with
  409 once closed, since no further reveals can arrive and a re-run cannot produce new
  results.

404 if not found, 503 if the current block can't be read to check the window.

After a reset the leader picks the competition up on its next loop tick; no restart
needed.

`POST /v1/competitions/{competition_id}/pause` (requires `Authorization: Bearer <ADMIN_API_KEY>`)
`POST /v1/competitions/{competition_id}/resume` (requires `Authorization: Bearer <ADMIN_API_KEY>`)

Halt the leader's scoring loop for one competition, and start it again — for stopping
a competition mid-flight without losing its state.

Pause stops only the leader's per-tick scoring work (stage 1 and stage 2) for that
competition. Weights already recorded keep distributing, followers are unaffected, and
block-based phases keep advancing — a long pause can run a competition past its
`scoring_end_block`, and the next unpaused tick then finalizes it with whatever was
scored.

Takes effect at the next tick boundary; work already in flight finishes. A candidate
left in `prechecking` keeps that status and resumes from there.

Both routes are idempotent. 404 if not found. Pause returns 409 once a competition has
finished scoring; resume has no such guard. `reset-scoring` clears the flag along with
the rest of the row. `paused_at` is exposed on `GET /v1/state/competitions/{id}`.


### 4. Run the benchmarks

You run your own benchmarks before committing, and pay for them yourself.

First, create an API key on the benchmark service: log in to its web GUI, add
credits, then create a key on the Tokens page. API keys can spend credits but
cannot buy them, so top up in the GUI first.

```bash
export BENCHMARK_API_KEY=bapi_...

tpn benchmark --wallet <coldkey> --competition <competition-id>
```

This quotes every benchmark the competition requires, shows the total price
against your available credit, and — once you confirm — submits each run
against exactly the repo, revision and `.gguf` file you uploaded in step 3. Run
ids are saved to your competition config as each one succeeds, ready for
`tpn commit`.

The command returns as soon as each run has an id; it does not wait for the
benchmarks to finish.

| Flag | Effect |
|---|---|
| `--only mmlu,gsm8k` | Run just these benchmarks |
| `--rerun` | Re-run benchmarks that already have a saved run id |
| `--yes` | Skip the price confirmation prompt |
| `--force-price` | Accept the current price without quoting first |

Re-running one benchmark is cheap: `tpn benchmark --only <name> --rerun`
replaces just that run id and leaves the others alone. Runs of the same model
from an earlier competition stay valid, so an unchanged model needs no
re-benchmarking.

A run must have **completed** before the competition's scoring phase starts.
There is no waiting period — a run still in progress at that point scores 0.0
for that benchmark. Check progress in the benchmark service GUI.

Driving the benchmark service directly is also fine: `tpn commit --runs`
accepts run ids from any source.

### 5. Commit

Submits a TimeLocked Commit to chain. Auto-reveals at `commit_end_block`.

```bash
tpn commit --wallet <coldkey> --competition <competition-id>
```

`tpn benchmark` already saved your run ids, so this normally needs no extra
input. To supply them yourself:

```bash
tpn commit -w <coldkey> -c <competition-id> \
  --runs '[{"b":"mmlu","r":"r1234"},{"b":"hellaswag","r":"r1235"}]'
```

A run id is either the service's short id (`r1234`) or the full UUID.

Validators verify every run id against your commit: the run must have
benchmarked the same repo, the same revision and the same file you committed.
A run that benchmarked anything else scores 0.0 for that benchmark, so commit
the same model you benchmarked.

Use `--dry-run` to inspect the payload without writing to chain.

```bash
tpn publish --wallet <coldkey> --competition <competition-id>
```

## docs/Overview.md
# TPN Subnet Overview (Miner Perspective)

## What you compete on

TPN rewards miners for producing **quantized GGUF versions of a base model** that are small and still accurate. Each competition defines a base model (`model_repo`), a set of benchmarks with minimum scores, and one of two ranking modes:

| `competition_type` | Pass/fail gate | Ranked by |
|---|---|---|
| `benchmark_floor` (default) | Every benchmark ≥ its `min_score` | **Lowest measured RAM** wins |
| `ram_ceiling` | Measured RAM ≤ `max_memory_kb` | **Highest minimum benchmark score** (your weakest benchmark) |

In `ram_ceiling`, a model is only as good as its weakest benchmark — a strong result on one cannot buy rank for a weak result on another.

Competitions are served by the leader validator (`GET /v1/competitions`); `tpn competitions` lists them.

## Competition timeline

Every competition moves through block-based phases:

```
start_block ──OPEN──▶ commit_end_block ──REVEALING──▶ +reveal_grace_blocks ──SCORING──▶ scoring_end_block ──DISTRIBUTING──▶ +distribution_blocks ──COMPLETE
```

- **OPEN** — upload, benchmark, commit.
- **REVEALING** — chain decrypts the timelocked commitments; validators wait out the grace period.
- **SCORING** — the leader verifies, ranks and prechecks submissions.
- **DISTRIBUTING** — validators set weights from the final ranking; emissions flow to winners.
- **COMPLETE** — the competition no longer receives emissions.

## Miner flow

1. **Register** your hotkey on the subnet (`tpn register`).
2. **Upload** your `.gguf` to a **private** HuggingFace repo (`tpn upload`). One repo per submission, exactly one `.gguf` in it. The CLI records repo, filename, **immutable commit SHA** (revision) and the file's **sha256**.
3. **Benchmark** the model yourself on the benchmark service (`tpn benchmark`, paid by you). Every run must be **completed** before the scoring phase starts — a run still in progress then scores 0.0.
4. **Commit** (`tpn commit`): writes a TimeLocked (TLE-encrypted) payload to chain:
   ```json
   {"spec":2,"competition_id":"…","repository":"user/repo","file":"model.gguf",
    "file_sha256":"…","max_memory":<KB>,"huggingface_revision":"<sha>",
    "runs":[{"b":"mmlu","r":"r1234"}, …]}
   ```
   Nobody can read it until the chain auto-decrypts it around `commit_end_block`, so submissions cannot be copied.
5. **Publish** the HF repo (`tpn publish`) before scoring starts. A private repo fails precheck.
6. **Monitor** with `tpn status`, or the leader's `GET /v1/state/competitions/{id}` (per-candidate status and failure reasons).

## Validator side: leader and followers

- One **leader** validator does the real work: reads chain, verifies runs, runs the precheck container, ranks, and publishes results via its API.
- **Followers** download nothing. They poll the leader's final results, compute the same emission weights locally and set weights on chain. When no competition is distributing, every validator copies stake-weighted consensus weights from chain.

## Scoring pipeline (leader)

### Stage 1 — reveal, verify, rank

1. **Scan reveals** from chain `RevealedCommitments`. A reveal is accepted only if it landed within `commit_end_block ± reveal_grace_blocks`, parses as a valid payload, and matches the competition id. **Banned hotkeys are skipped**; unregistered hotkeys are dropped.
2. **Dedup**: if several hotkeys reveal the same `file_sha256`, the **earliest reveal block** wins; the others fail as duplicates. Copying someone's file gains nothing.
3. **Verify runs**: for each competition benchmark, the leader fetches your run id from the benchmark coordinator and accepts it only if:
   - status is `completed`
   - repo matches yours (case-insensitive)
   - it used exactly your committed **revision**
   - your committed **file** is among the run's loaded model files
   - where HF exposes an LFS sha256, it matches your `file_sha256`
   - the run covers that benchmark, the benchmark completed, and it has a score

   Any failure → **that benchmark scores 0.0**. Not fatal by itself, but it will almost certainly fail the floors later. A missing run id also scores 0.0.
4. **Rank** candidates by provisional final score from the verified scores. For `benchmark_floor`, RAM is not yet measured, so this ranking uses your **self-reported** `max_memory`.

### Stage 2 — precheck, in rank order

The leader prechecks **one candidate per loop tick**, top rank first, until `top_n` candidates are scored, candidates run out, or `scoring_end_block` hits. A candidate that fails is marked `failed` and the next one moves up (backfill).

Precheck passes when:
- the HF repo is public
- the committed filename exists at the committed revision
- the **precheck container** (below) accepts the model
- measured RAM is within **±1%** of your reported `max_memory` (`RAM_CHECK_LYING_TOLERANCE`, default 0.01)

After precheck:
- every verified benchmark score must be ≥ its `min_score`
- for `ram_ceiling`: measured RAM must be ≤ `max_memory_kb`

Then the candidate is **scored**:
- `benchmark_floor`: `final_score = −measured_memory_kb` (less RAM ranks higher)
- `ram_ceiling`: `final_score = min(verified benchmark scores)`

### Stage 3 — finalize and set weights

Scored candidates are sorted by `final_score` (descending). Rank *i* receives `emission_distribution[i]` of the competition's pool; ranks past `top_n` get 0.

**Weights only start at `scoring_end_block`**, even if all `top_n` candidates were scored earlier. Finalized results are recorded as soon as scoring completes, but validators only push them on chain once the competition enters the DISTRIBUTING phase, and keep doing so until `scoring_end_block + distribution_blocks`.

While a competition is distributing, each validator:
- sums every distributing competition's shares, scaled by its `emission_weight`
- drops winners no longer registered (their share is not redistributed)
- burns any unallocated weight to uid 0

## The precheck container

A Docker image (`ghcr.io/taofu-labs/tpn-precheck`, built from `shared/validation/precheck.Dockerfile`), public on GHCR. The leader starts one per competition. It runs a small FastAPI service with a pinned CPU build of llama.cpp (`b10020`).

**On startup** it downloads the competition's base model (`model_repo`) once. `/health` reports ready when done.

**`POST /check`** (validator path) downloads your GGUF at the exact committed repo/revision/filename (rejects files > 50 GiB), runs three independent checks, then deletes the file:

1. **Provenance — is this really derived from the base model?**
   - *Tokenizer*: tokenizer type, vocab size and BPE merge count must match exactly; individual entries may differ < 1% (allows added chat-template tokens).
   - *Embedding CKA*: samples 4096 rows of `token_embd.weight` from both models, dequantizes them and computes linear Centered Kernel Alignment. Must be **≥ 0.80**. CKA is invariant to rotation, permutation and scaling, so quantizing or pruning the real base model keeps it high; an unrelated or from-scratch/distilled model falls below the threshold.
   - Fail → `provenance fail`.
2. **RAM measurement**: runs `llama-cli` CPU-only (`-ngl 0`, `-c <ram_check_context_length>` (default 4096), f16 KV cache, `--no-mmap`, generates 1 token) and parses llama.cpp's logged CPU weight and KV-cache buffer sizes. **Measured RAM = weights + KV cache.** Load failure, timeout (600s), OOM kill, or no CPU weight buffer → fail.
3. **sha256** of the downloaded file, compared against your committed `file_sha256`. **A mismatch permanently bans your hotkey** — banned hotkeys are skipped in every future competition.

**`POST /check-local`** (miner self-check) reads a file from a `/data` volume mount and runs the RAM measurement and sha256 (no provenance). Use it to get the exact `max_memory` value before committing:

```bash
docker run -d -p 8080:8080 -v $(pwd):/data ghcr.io/taofu-labs/tpn-precheck
curl -X POST localhost:8080/check-local \
  -H 'content-type: application/json' \
  -d '{"path":"/data/my-model.gguf","context_length":4096}'
# commit ram.ram_bytes / 1024 as max_memory (KB)
```

## Ways to lose (in pipeline order)

| Failure | Consequence |
|---|---|
| Reveal outside grace window / malformed payload / wrong competition id | Not considered |
| Same sha256 as an earlier reveal | Dedup loss |
| Run not completed, or benchmarked a different repo/revision/file | That benchmark = 0.0 |
| Repo private, or file missing at revision | Precheck fail (backfilled) |
| Tokenizer or CKA mismatch with base model | Precheck fail |
| llama-cli can't load the model | Precheck fail |
| Reported `max_memory` off by > 1% from measured RAM | Precheck fail |
| sha256 mismatch | Precheck fail **+ permanent ban** |
| Below a benchmark floor / above the RAM cap | Not scored |
| Ranked below `top_n` | 0 weight |

## Practical tips

- Commit exactly the revision and file you benchmarked; don't push to the repo after benchmarking.
- Measure `max_memory` with `/check-local` at the competition's `ram_check_context_length` — don't guess.
- Make sure every benchmark run has completed before the scoring phase starts.
- Publish the repo before scoring starts.
- In `benchmark_floor`, you're prechecked in order of your *claimed* RAM but paid on *measured* RAM, and a claim off by more than 1% fails outright.
- Emissions only start flowing at `scoring_end_block`, not when your candidate is scored.

### Mocked benchmark runs on localnet

Miners own their run ids in the live flow — the validator only polls them — so
`MockCoordinator` reports any id it did not generate itself as
`unknown run_id`. To drive a full localnet competition with benchmarks mocked
and everything else real, pre-register the ids in a JSON file and point
`MOCK_RUNS_FILE` at it:

```json
{
  "r1001": {
    "repo": "owner/model-GGUF",
    "revision": "<immutable commit sha>",
    "file": "model-q4.gguf",
    "file_sha256": "<64 hex>",
    "benchmark": "mmlu",
    "score": 0.82
  }
}
```

```bash
MOCK_RUNS_FILE=./mock_runs.json TPN_DOTENV_PATH=.env.localnet \
  uv run --package validator python src/validator/main.py
```

`repo`, `revision` and `file` must match what the miner commits, or the run is
rejected exactly as a real mismatch would be. An id absent from the file still
fails, so verification is never weakened. Only `MockCoordinator` reads this —
`BENCHMARK_BACKEND=http` ignores it.

### Commit reveals on a fast-runtime chain

TLE reveals are scheduled in drand rounds (wall-clock), but `scan_reveals`
accepts them by block height, within `reveal_grace_blocks` of
`commit_end_block`. The two only line up while `--block-time` matches the
chain's real rate.

Localnet's fast runtime drifts enough for this to matter: a commit placed far
ahead of `commit_end_block` can auto-decrypt a hundred blocks early and get
discarded, ending the competition with `failed_no_reveals` despite a perfectly
valid payload. Mainnet holds close to 12s, so the default 150-block grace
absorbs it there.

When testing on localnet: measure the real block rate, pass it as
`--block-time`, keep the commit window short, and give the competition a
generous `reveal_grace_blocks`. If reveals are being dropped, the validator
logs the reason at DEBUG:

    reveal_block=1017 outside window for commit_end_block=1133

## shared/validation/README.md
# GGUF Model Provenance Checker

Prescreen whether GGUF model B is plausibly derived from model A. Two static gates — no inference, no GPU. Stops early on hard disproof.

## Checks

**Check 1 — Tokenizer:** Compares tokenizer type, vocabulary, and BPE merge rules. Vocab size or merge count mismatch is a hard disproof. Entry differences <1% pass (common in fine-tunes that add chat-template tokens).

**Check 2 — Embedding CKA:** Samples `n_tokens` rows from `token_embd.weight` and computes linear Centered Kernel Alignment between A and B. CKA is invariant to rotation, permutation, and isotropic scaling, so it stays high under quantization/pruning and drops to the independent-model baseline otherwise. Pass if CKA ≥ threshold.

---

## Requirements

Python 3.11+ with:

```bash
pip install gguf numpy
```

---

## Run

```bash
python provenance_check.py model_a.gguf model_b.gguf
python provenance_check.py model_a.gguf model_b.gguf --threshold 0.85
python provenance_check.py model_a.gguf model_b.gguf --n-tokens 2048 --seed 123
```

**Flags:**

| Flag | Default | Description |
|------|---------|-------------|
| `--threshold` | `0.80` | CKA accept threshold — calibrate against known-independent same-tokenizer models |
| `--n-tokens` | `4096` | Token rows sampled for CKA |
| `--seed` | `42` | RNG seed for reproducible sampling |

Exit code `0` = plausible derivative, `1` = not a plausible derivative, `2` = input error.

---

## Interpreting results

| Result | Meaning |
|--------|---------|
| **PASS** (both checks) | B is a plausible derivative of A — confirm via benchmark |
| **FAIL** (tokenizer) | Hard disproof: different vocab/merges |
| **FAIL** (CKA) | Embedding geometry too different; not a plausible derivative |

The threshold MUST be calibrated: measure CKA for a few known-independent models that share the same tokenizer, then set the gate above that baseline.


---

## Limitations

- **Prescreen only.** A PASS is not confirmation — follow up with benchmarking.
- **Quantized tensors supported.** `_dequant_rows` dequantizes on the fly; requires `embed_dim % block_size == 0` (all valid GGUF files satisfy this).
- **Cannot detect weight replacement.** A model could share the tokenizer but have entirely retrained embeddings; Check 2 would catch this, but only if the CKA threshold is set correctly.
- **From-scratch / distilled models correctly fail.** They share no weights with A and will fall below the CKA threshold.
- **For high-stakes decisions**, follow up with dynamic checks: run both models on the same prompt distribution and compare output logits or KL-divergence.

# TPN Validator

Two validator modes, controlled by `VALIDATOR_MODE` (`.env`):

- **leader** (default) — scans chain reveals, verifies the benchmark run ids
  miners committed, ranks on those verified scores, prechecks the top candidates,
  computes and sets weights, persists every scoring run to SQLite, and serves a
  read-only HTTP API for followers and dashboards.
- **follower** — parses competitions itself but reads scoring results from a leader
  validator's API instead of verifying/prechecking. Recomputes emission weights
  locally from the leader's `ScoringResult`s and sets its own weights.

Both modes run the same chain-copy `weight_loop()` fallback in parallel — if a
follower can't reach its leader, it just skips that competition's cycle and keeps
submitting stake-weighted consensus weights from chain until the leader is reachable
again.

## Persistence

All validator state (scored competitions, bans, and — leader-only — full scoring
history and weights history) lives in a single SQLite file:

```
~/.tpn/validator-storage/validator.db      # POSIX
%APPDATA%/tpn/validator-storage/validator.db  # Windows
```

`python main.py --clean` wipes it before starting.

## Configuration

### Common (both modes)

```
VALIDATOR_MODE=leader              # "leader" | "follower"
```

### Leader mode

```
LEADER_API_HOST=0.0.0.0
LEADER_API_PORT=9200
```

```
ADMIN_API_KEY=                     # required to enable POST /v1/competitions
```

Run the leader's API behind a reverse proxy (HTTPS). The read endpoints
(`/v1/follower/*`, `/v1/state/*`, `GET /v1/competitions*`) have no auth — treat them
as public read access. `POST /v1/competitions` is bearer-token gated
(`Authorization: Bearer <ADMIN_API_KEY>`) and **must** be served over HTTPS in any
real deployment — a bearer token sent over plain HTTP is sniffable in transit.
Generate the key once with `python -c "import secrets; print(secrets.token_urlsafe(32))"`
and store it as a deploy secret. Leaving `ADMIN_API_KEY` unset disables the write
endpoint (503), it does not make it public.

### Follower mode

```
LEADER_VALIDATOR_URL=https://val0.trueperformancenetwork.com   # required
FOLLOWER_POLL_INTERVAL=60
```

## Leader API

`GET /v1/follower/scoring-results?competition_id=X`
Final scoring results for one competition. This is what followers poll to set
weights. `competition_id` is required — 400 without it.

```json
{
  "results": [
    {"competition_id": "tpn-001", "hotkey": "5F...", "final_score": -812345,
     "max_memory_kb": 812345, "finalized_at": 1756100000.0}
  ],
  "scored_status": "scored"
}
```

`results` is empty until the competition reaches stage `finalized`, so followers
never see partial rankings. `scored_status` is `null` before scoring starts, then
one of `scored`, `failed_no_reveals`, `failed_no_participants`, or
`failed_stage1_infra`. An empty `results` with a `failed_*` status means the leader
gave up and no weights will ever be published for that competition.

`GET /v1/state/competitions/{competition_id}`
Full detail for a competition: revealed candidates with their status and failure
reasons, benchmark results, scoring results, and weights history. Superset of the
follower endpoints — dashboards should use this instead of stitching
`/v1/follower/*` calls together. 404 if no competition with that id exists.

`GET /v1/state/status`
Leader's task/loop status (same shape as `get_validator_status()`).

`GET /v1/state/weights-history?competition_id=X`
Past weight submissions for a competition.

`GET /v1/competitions`
All competitions. `?active=true&block=N` filters to active ones at block `N`
(current chain block if `block` omitted). This is what followers, the miner CLI,
and dashboards should read competition config from. 400 if `block` is not a
non-negative integer.

`GET /v1/competitions/{competition_id}`
Single competition spec. 404 if not found.

`POST /v1/competitions` (requires `Authorization: Bearer <ADMIN_API_KEY>`)
Create or update (upsert by `id`) one competition. Body is a full `CompetitionSpec`
JSON object — validated the same way as `competitions/*.json` was before this moved
off GitHub. 401 on missing/invalid token, 503 if `ADMIN_API_KEY` isn't set, 422 on a
spec that fails validation. 413 on a body over 256 KB.

`DELETE /v1/competitions/{competition_id}` (requires `Authorization: Bearer <ADMIN_API_KEY>`)
Remove one competition spec — intended for an id pushed by mistake, before anything
has been scored against it. 404 if not found, 401/503 on auth as above.

Refuses with 409 once the competition has scoring state (reveals, run verifications,
scoring results, weights, or a scoring stage), because those tables key off
`competition_id` with no foreign key — dropping the spec would leave their rows
unreachable but still present. Append `?force=true` to delete the spec anyway;
the scoring rows for that id are left in place.

`POST /v1/competitions/{competition_id}/reset-scoring` (requires `Authorization: Bearer <ADMIN_API_KEY>`)
Clear scoring state so the competition re-runs from stage 1. For a competition that
gave up on a transient failure — `failed_stage1_infra` (coordinator unreachable, chain
scan failed), `failed_no_reveals`, or `failed_no_participants` — while its scoring
window is still open. Without this the only recovery was `--clean`, which wipes every
competition's history plus the ban list.

Deletes that competition's `revealed_candidates`, `benchmark_results`,
`scoring_results`, and its `scored_competitions` row, and reports
the per-table counts. **Bans and weights history are preserved** — a ban records
proven miner misbehaviour that a validator-side infra failure does not undo, and
weights history stays as an audit trail of what was already set on chain.

**There is no override.** A reset is allowed only when both hold:

- The competition's stage is `stage1_ranking` (including a competition that has not
  been touched yet), `failed_no_reveals`, `failed_no_participants`, or
  `failed_stage1_infra`. A competition in `stage2_scoring` or `finalized` is refused
  with 409 — stage 2 is mid-run, and a finalized competition already had weights
  computed and published from its result.
- Its scoring window is still open (`current_block < scoring_end_block`). Refused with
  409 once closed, since no further reveals can arrive and a re-run cannot produce new
  results.

404 if not found, 503 if the current block can't be read to check the window.

After a reset the leader picks the competition up on its next loop tick; no restart
needed.

`POST /v1/competitions/{competition_id}/pause` (requires `Authorization: Bearer <ADMIN_API_KEY>`)
`POST /v1/competitions/{competition_id}/resume` (requires `Authorization: Bearer <ADMIN_API_KEY>`)

Halt the leader's scoring loop for one competition, and start it again — for stopping
a competition mid-flight without losing its state.

Pause stops only the leader's per-tick scoring work (stage 1 and stage 2) for that
competition. Weights already recorded keep distributing, followers are unaffected, and
block-based phases keep advancing — a long pause can run a competition past its
`scoring_end_block`, and the next unpaused tick then finalizes it with whatever was
scored.

Takes effect at the next tick boundary; work already in flight finishes. A candidate
left in `prechecking` keeps that status and resumes from there.

Both routes are idempotent. 404 if not found. Pause returns 409 once a competition has
finished scoring; resume has no such guard. `reset-scoring` clears the flag along with
the rest of the row. `paused_at` is exposed on `GET /v1/state/competitions/{id}`.

```bash
tpn competitions
```

Uploads your `.gguf` file to a private HF repo and saves upload metadata locally.

```bash
tpn upload ./my-model.gguf \
  --repo my-model-q4 \
```

### 4. Run the benchmarks

You run your own benchmarks before committing, and pay for them yourself.

First, create an API key on the benchmark service: log in to its web GUI, add
credits, then create a key on the Tokens page. API keys can spend credits but
cannot buy them, so top up in the GUI first.

```bash
export BENCHMARK_API_KEY=bapi_...

tpn benchmark --wallet <coldkey> --competition <competition-id>
```

This quotes every benchmark the competition requires, shows the total price
against your available credit, and — once you confirm — submits each run
against exactly the repo, revision and `.gguf` file you uploaded in step 3. Run
ids are saved to your competition config as each one succeeds, ready for
`tpn commit`.

The command returns as soon as each run has an id; it does not wait for the
benchmarks to finish.

| Flag | Effect |
|---|---|
| `--only mmlu,gsm8k` | Run just these benchmarks |
| `--rerun` | Re-run benchmarks that already have a saved run id |
| `--yes` | Skip the price confirmation prompt |
| `--force-price` | Accept the current price without quoting first |

Re-running one benchmark is cheap: `tpn benchmark --only <name> --rerun`
replaces just that run id and leaves the others alone. Runs of the same model
from an earlier competition stay valid, so an unchanged model needs no
re-benchmarking.

A run must have **completed** before the competition's scoring phase starts.
There is no waiting period — a run still in progress at that point scores 0.0
for that benchmark. Check progress in the benchmark service GUI.

Driving the benchmark service directly is also fine: `tpn commit --runs`
accepts run ids from any source.

Submits a TimeLocked Commit to chain. Auto-reveals at `commit_end_block`.

```bash
tpn commit --wallet <coldkey> --competition <competition-id>
```

`tpn benchmark` already saved your run ids, so this normally needs no extra
input. To supply them yourself:

```bash
tpn commit -w <coldkey> -c <competition-id> \
  --runs '[{"b":"mmlu","r":"r1234"},{"b":"hellaswag","r":"r1235"}]'
```

A run id is either the service's short id (`r1234`) or the full UUID.

Validators verify every run id against your commit: the run must have
benchmarked the same repo, the same revision and the same file you committed.
A run that benchmarked anything else scores 0.0 for that benchmark, so commit
the same model you benchmarked.

Use `--dry-run` to inspect the payload without writing to chain.

Makes the HF repo public so validators can download your model. Do this before the scoring phase begins.

```bash
tpn publish --wallet <coldkey> --competition <competition-id>
```

```bash
tpn status --wallet <coldkey>
```

## docs/Overview.md
# TPN Subnet Overview (Miner Perspective)

## What you compete on

TPN rewards miners for producing **quantized GGUF versions of a base model** that are small and still accurate. Each competition defines a base model (`model_repo`), a set of benchmarks with minimum scores, and one of two ranking modes:

| `competition_type` | Pass/fail gate | Ranked by |
|---|---|---|
| `benchmark_floor` (default) | Every benchmark ≥ its `min_score` | **Lowest measured RAM** wins |
| `ram_ceiling` | Measured RAM ≤ `max_memory_kb` | **Highest minimum benchmark score** (your weakest benchmark) |

In `ram_ceiling`, a model is only as good as its weakest benchmark — a strong result on one cannot buy rank for a weak result on another.

Competitions are served by the leader validator (`GET /v1/competitions`); `tpn competitions` lists them.

## Competition timeline

Every competition moves through block-based phases:

```
start_block ──OPEN──▶ commit_end_block ──REVEALING──▶ +reveal_grace_blocks ──SCORING──▶ scoring_end_block ──DISTRIBUTING──▶ +distribution_blocks ──COMPLETE
```

- **OPEN** — upload, benchmark, commit.
- **REVEALING** — chain decrypts the timelocked commitments; validators wait out the grace period.
- **SCORING** — the leader verifies, ranks and prechecks submissions.
- **DISTRIBUTING** — validators set weights from the final ranking; emissions flow to winners.
- **COMPLETE** — the competition no longer receives emissions.

## Miner flow

1. **Register** your hotkey on the subnet (`tpn register`).
2. **Upload** your `.gguf` to a **private** HuggingFace repo (`tpn upload`). One repo per submission, exactly one `.gguf` in it. The CLI records repo, filename, **immutable commit SHA** (revision) and the file's **sha256**.
3. **Benchmark** the model yourself on the benchmark service (`tpn benchmark`, paid by you). Every run must be **completed** before the scoring phase starts — a run still in progress then scores 0.0.
4. **Commit** (`tpn commit`): writes a TimeLocked (TLE-encrypted) payload to chain:
   ```json
   {"spec":2,"competition_id":"…","repository":"user/repo","file":"model.gguf",
    "file_sha256":"…","max_memory":<KB>,"huggingface_revision":"<sha>",
    "runs":[{"b":"mmlu","r":"r1234"}, …]}
   ```
   Nobody can read it until the chain auto-decrypts it around `commit_end_block`, so submissions cannot be copied.
5. **Publish** the HF repo (`tpn publish`) before scoring starts. A private repo fails precheck.
6. **Monitor** with `tpn status`, or the leader's `GET /v1/state/competitions/{id}` (per-candidate status and failure reasons).

## Validator side: leader and followers

- One **leader** validator does the real work: reads chain, verifies runs, runs the precheck container, ranks, and publishes results via its API.
- **Followers** download nothing. They poll the leader's final results, compute the same emission weights locally and set weights on chain. When no competition is distributing, every validator copies stake-weighted consensus weights from chain.

## Scoring pipeline (leader)

### Stage 1 — reveal, verify, rank

1. **Scan reveals** from chain `RevealedCommitments`. A reveal is accepted only if it landed within `commit_end_block ± reveal_grace_blocks`, parses as a valid payload, and matches the competition id. **Banned hotkeys are skipped**; unregistered hotkeys are dropped.
2. **Dedup**: if several hotkeys reveal the same `file_sha256`, the **earliest reveal block** wins; the others fail as duplicates. Copying someone's file gains nothing.
3. **Verify runs**: for each competition benchmark, the leader fetches your run id from the benchmark coordinator and accepts it only if:
   - status is `completed`
   - repo matches yours (case-insensitive)
   - it used exactly your committed **revision**
   - your committed **file** is among the run's loaded model files
   - where HF exposes an LFS sha256, it matches your `file_sha256`
   - the run covers that benchmark, the benchmark completed, and it has a score

   Any failure → **that benchmark scores 0.0**. Not fatal by itself, but it will almost certainly fail the floors later. A missing run id also scores 0.0.
4. **Rank** candidates by provisional final score from the verified scores. For `benchmark_floor`, RAM is not yet measured, so this ranking uses your **self-reported** `max_memory`.

### Stage 2 — precheck, in rank order

The leader prechecks **one candidate per loop tick**, top rank first, until `top_n` candidates are scored, candidates run out, or `scoring_end_block` hits. A candidate that fails is marked `failed` and the next one moves up (backfill).

Precheck passes when:
- the HF repo is public
- the committed filename exists at the committed revision
- the **precheck container** (below) accepts the model
- measured RAM is within **±1%** of your reported `max_memory` (`RAM_CHECK_LYING_TOLERANCE`, default 0.01)

After precheck:
- every verified benchmark score must be ≥ its `min_score`
- for `ram_ceiling`: measured RAM must be ≤ `max_memory_kb`

Then the candidate is **scored**:
- `benchmark_floor`: `final_score = −measured_memory_kb` (less RAM ranks higher)
- `ram_ceiling`: `final_score = min(verified benchmark scores)`

### Stage 3 — finalize and set weights

Scored candidates are sorted by `final_score` (descending). Rank *i* receives `emission_distribution[i]` of the competition's pool; ranks past `top_n` get 0.

**Weights only start at `scoring_end_block`**, even if all `top_n` candidates were scored earlier. Finalized results are recorded as soon as scoring completes, but validators only push them on chain once the competition enters the DISTRIBUTING phase, and keep doing so until `scoring_end_block + distribution_blocks`.

While a competition is distributing, each validator:
- sums every distributing competition's shares, scaled by its `emission_weight`
- drops winners no longer registered (their share is not redistributed)
- burns any unallocated weight to uid 0

## The precheck container

A Docker image (`ghcr.io/taofu-labs/tpn-precheck`, built from `shared/validation/precheck.Dockerfile`), public on GHCR. The leader starts one per competition. It runs a small FastAPI service with a pinned CPU build of llama.cpp (`b10020`).

**On startup** it downloads the competition's base model (`model_repo`) once. `/health` reports ready when done.

**`POST /check`** (validator path) downloads your GGUF at the exact committed repo/revision/filename (rejects files > 50 GiB), runs three independent checks, then deletes the file:

1. **Provenance — is this really derived from the base model?**
   - *Tokenizer*: tokenizer type, vocab size and BPE merge count must match exactly; individual entries may differ < 1% (allows added chat-template tokens).
   - *Embedding CKA*: samples 4096 rows of `token_embd.weight` from both models, dequantizes them and computes linear Centered Kernel Alignment. Must be **≥ 0.80**. CKA is invariant to rotation, permutation and scaling, so quantizing or pruning the real base model keeps it high; an unrelated or from-scratch/distilled model falls below the threshold.
   - Fail → `provenance fail`.
2. **RAM measurement**: runs `llama-cli` CPU-only (`-ngl 0`, `-c <ram_check_context_length>` (default 4096), f16 KV cache, `--no-mmap`, generates 1 token) and parses llama.cpp's logged CPU weight and KV-cache buffer sizes. **Measured RAM = weights + KV cache.** Load failure, timeout (600s), OOM kill, or no CPU weight buffer → fail.
3. **sha256** of the downloaded file, compared against your committed `file_sha256`. **A mismatch permanently bans your hotkey** — banned hotkeys are skipped in every future competition.

**`POST /check-local`** (miner self-check) reads a file from a `/data` volume mount and runs the RAM measurement and sha256 (no provenance). Use it to get the exact `max_memory` value before committing:

```bash
docker run -d -p 8080:8080 -v $(pwd):/data ghcr.io/taofu-labs/tpn-precheck
curl -X POST localhost:8080/check-local \
  -H 'content-type: application/json' \
  -d '{"path":"/data/my-model.gguf","context_length":4096}'
# commit ram.ram_bytes / 1024 as max_memory (KB)
```

## Ways to lose (in pipeline order)

| Failure | Consequence |
|---|---|
| Reveal outside grace window / malformed payload / wrong competition id | Not considered |
| Same sha256 as an earlier reveal | Dedup loss |
| Run not completed, or benchmarked a different repo/revision/file | That benchmark = 0.0 |
| Repo private, or file missing at revision | Precheck fail (backfilled) |
| Tokenizer or CKA mismatch with base model | Precheck fail |
| llama-cli can't load the model | Precheck fail |
| Reported `max_memory` off by > 1% from measured RAM | Precheck fail |
| sha256 mismatch | Precheck fail **+ permanent ban** |
| Below a benchmark floor / above the RAM cap | Not scored |
| Ranked below `top_n` | 0 weight |

## Practical tips

- Commit exactly the revision and file you benchmarked; don't push to the repo after benchmarking.
- Measure `max_memory` with `/check-local` at the competition's `ram_check_context_length` — don't guess.
- Make sure every benchmark run has completed before the scoring phase starts.
- Publish the repo before scoring starts.
- In `benchmark_floor`, you're prechecked in order of your *claimed* RAM but paid on *measured* RAM, and a claim off by more than 1% fails outright.
- Emissions only start flowing at `scoring_end_block`, not when your candidate is scored.

Miners own their run ids in the live flow — the validator only polls them — so
`MockCoordinator` reports any id it did not generate itself as
`unknown run_id`. To drive a full localnet competition with benchmarks mocked
and everything else real, pre-register the ids in a JSON file and point
`MOCK_RUNS_FILE` at it:

```json
{
  "r1001": {
    "repo": "owner/model-GGUF",
    "revision": "<immutable commit sha>",
```


`repo`, `revision` and `file` must match what the miner commits, or the run is

### Commit reveals on a fast-runtime chain

TLE reveals are scheduled in drand rounds (wall-clock), but `scan_reveals`
accepts them by block height, within `reveal_grace_blocks` of
`commit_end_block`. The two only line up while `--block-time` matches the
chain's real rate.

Localnet's fast runtime drifts enough for this to matter: a commit placed far
ahead of `commit_end_block` can auto-decrypt a hundred blocks early and get
discarded, ending the competition with `failed_no_reveals` despite a perfectly
valid payload. Mainnet holds close to 12s, so the default 150-block grace
absorbs it there.

When testing on localnet: measure the real block rate, pass it as
`--block-time`, keep the commit window short, and give the competition a
generous `reveal_grace_blocks`. If reveals are being dropped, the validator
logs the reason at DEBUG:

    reveal_block=1017 outside window for commit_end_block=1133

# GGUF Model Provenance Checker

Prescreen whether GGUF model B is plausibly derived from model A. Two static gates — no inference, no GPU. Stops early on hard disproof.

## Checks

**Check 1 — Tokenizer:** Compares tokenizer type, vocabulary, and BPE merge rules. Vocab size or merge count mismatch is a hard disproof. Entry differences <1% pass (common in fine-tunes that add chat-template tokens).

**Check 2 — Embedding CKA:** Samples `n_tokens` rows from `token_embd.weight` and computes linear Centered Kernel Alignment between A and B. CKA is invariant to rotation, permutation, and isotropic scaling, so it stays high under quantization/pruning and drops to the independent-model baseline otherwise. Pass if CKA ≥ threshold.

---

## Requirements

Python 3.11+ with:

```bash
pip install gguf numpy
```

---

## Run

```bash
python provenance_check.py model_a.gguf model_b.gguf
python provenance_check.py model_a.gguf model_b.gguf --threshold 0.85
python provenance_check.py model_a.gguf model_b.gguf --n-tokens 2048 --seed 123
```

**Flags:**

| Flag | Default | Description |
|------|---------|-------------|
| `--threshold` | `0.80` | CKA accept threshold — calibrate against known-independent same-tokenizer models |
| `--n-tokens` | `4096` | Token rows sampled for CKA |
| `--seed` | `42` | RNG seed for reproducible sampling |

Exit code `0` = plausible derivative, `1` = not a plausible derivative, `2` = input error.

---

## Interpreting results

| Result | Meaning |
|--------|---------|
| **PASS** (both checks) | B is a plausible derivative of A — confirm via benchmark |
| **FAIL** (tokenizer) | Hard disproof: different vocab/merges |
| **FAIL** (CKA) | Embedding geometry too different; not a plausible derivative |

The threshold MUST be calibrated: measure CKA for a few known-independent models that share the same tokenizer, then set the gate above that baseline.


---

## Limitations

- **Prescreen only.** A PASS is not confirmation — follow up with benchmarking.
- **Quantized tensors supported.** `_dequant_rows` dequantizes on the fly; requires `embed_dim % block_size == 0` (all valid GGUF files satisfy this).
- **Cannot detect weight replacement.** A model could share the tokenizer but have entirely retrained embeddings; Check 2 would catch this, but only if the CKA threshold is set correctly.
- **From-scratch / distilled models correctly fail.** They share no weights with A and will fall below the CKA threshold.
- **For high-stakes decisions**, follow up with dynamic checks: run both models on the same prompt distribution and compare output logits or KL-divergence.

# TPN Validator

Two validator modes, controlled by `VALIDATOR_MODE` (`.env`):

- **leader** (default) — scans chain reveals, verifies the benchmark run ids
  miners committed, ranks on those verified scores, prechecks the top candidates,
  computes and sets weights, persists every scoring run to SQLite, and serves a
  read-only HTTP API for followers and dashboards.
- **follower** — parses competitions itself but reads scoring results from a leader
  validator's API instead of verifying/prechecking. Recomputes emission weights
  locally from the leader's `ScoringResult`s and sets its own weights.

Both modes run the same chain-copy `weight_loop()` fallback in parallel — if a
follower can't reach its leader, it just skips that competition's cycle and keeps
submitting stake-weighted consensus weights from chain until the leader is reachable
again.

## Persistence

All validator state (scored competitions, bans, and — leader-only — full scoring
history and weights history) lives in a single SQLite file:

```
~/.tpn/validator-storage/validator.db      # POSIX
%APPDATA%/tpn/validator-storage/validator.db  # Windows
```

`python main.py --clean` wipes it before starting.

## Configuration

### Common (both modes)

```
VALIDATOR_MODE=leader              # "leader" | "follower"
```

### Leader mode

```
LEADER_API_HOST=0.0.0.0
LEADER_API_PORT=9200
```

```
ADMIN_API_KEY=                     # required to enable POST /v1/competitions
```

Run the leader's API behind a reverse proxy (HTTPS). The read endpoints
(`/v1/follower/*`, `/v1/state/*`, `GET /v1/competitions*`) have no auth — treat them
as public read access. `POST /v1/competitions` is bearer-token gated
(`Authorization: Bearer <ADMIN_API_KEY>`) and **must** be served over HTTPS in any
real deployment — a bearer token sent over plain HTTP is sniffable in transit.
Generate the key once with `python -c "import secrets; print(secrets.token_urlsafe(32))"`
and store it as a deploy secret. Leaving `ADMIN_API_KEY` unset disables the write
endpoint (503), it does not make it public.

### Follower mode

```
LEADER_VALIDATOR_URL=https://val0.trueperformancenetwork.com   # required
FOLLOWER_POLL_INTERVAL=60
```

## Leader API

`GET /v1/follower/scoring-results?competition_id=X`
Final scoring results for one competition. This is what followers poll to set
weights. `competition_id` is required — 400 without it.

```json
{
  "results": [
    {"competition_id": "tpn-001", "hotkey": "5F...", "final_score": -812345,
     "max_memory_kb": 812345, "finalized_at": 1756100000.0}
  ],
  "scored_status": "scored"
}
```

`results` is empty until the competition reaches stage `finalized`, so followers
never see partial rankings. `scored_status` is `null` before scoring starts, then
one of `scored`, `failed_no_reveals`, `failed_no_participants`, or
`failed_stage1_infra`. An empty `results` with a `failed_*` status means the leader
gave up and no weights will ever be published for that competition.

`GET /v1/state/competitions/{competition_id}`
Full detail for a competition: revealed candidates with their status and failure
reasons, benchmark results, scoring results, and weights history. Superset of the
follower endpoints — dashboards should use this instead of stitching
`/v1/follower/*` calls together. 404 if no competition with that id exists.

`GET /v1/state/status`
Leader's task/loop status (same shape as `get_validator_status()`).

`GET /v1/state/weights-history?competition_id=X`
Past weight submissions for a competition.

`GET /v1/competitions`
All competitions. `?active=true&block=N` filters to active ones at block `N`
(current chain block if `block` omitted). This is what followers, the miner CLI,
and dashboards should read competition config from. 400 if `block` is not a
non-negative integer.

`GET /v1/competitions/{competition_id}`
Single competition spec. 404 if not found.

`POST /v1/competitions` (requires `Authorization: Bearer <ADMIN_API_KEY>`)
Create or update (upsert by `id`) one competition. Body is a full `CompetitionSpec`
JSON object — validated the same way as `competitions/*.json` was before this moved
off GitHub. 401 on missing/invalid token, 503 if `ADMIN_API_KEY` isn't set, 422 on a
spec that fails validation. 413 on a body over 256 KB.

`DELETE /v1/competitions/{competition_id}` (requires `Authorization: Bearer <ADMIN_API_KEY>`)
Remove one competition spec — intended for an id pushed by mistake, before anything
has been scored against it. 404 if not found, 401/503 on auth as above.

Refuses with 409 once the competition has scoring state (reveals, run verifications,
scoring results, weights, or a scoring stage), because those tables key off
`competition_id` with no foreign key — dropping the spec would leave their rows
unreachable but still present. Append `?force=true` to delete the spec anyway;
the scoring rows for that id are left in place.

`POST /v1/competitions/{competition_id}/reset-scoring` (requires `Authorization: Bearer <ADMIN_API_KEY>`)
Clear scoring state so the competition re-runs from stage 1. For a competition that
gave up on a transient failure — `failed_stage1_infra` (coordinator unreachable, chain
scan failed), `failed_no_reveals`, or `failed_no_participants` — while its scoring
window is still open. Without this the only recovery was `--clean`, which wipes every
competition's history plus the ban list.

Deletes that competition's `revealed_candidates`, `benchmark_results`,
`scoring_results`, and its `scored_competitions` row, and reports
the per-table counts. **Bans and weights history are preserved** — a ban records
proven miner misbehaviour that a validator-side infra failure does not undo, and
weights history stays as an audit trail of what was already set on chain.

**There is no override.** A reset is allowed only when both hold:

- The competition's stage is `stage1_ranking` (including a competition that has not
  been touched yet), `failed_no_reveals`, `failed_no_participants`, or
  `failed_stage1_infra`. A competition in `stage2_scoring` or `finalized` is refused
  with 409 — stage 2 is mid-run, and a finalized competition already had weights
  computed and published from its result.
- Its scoring window is still open (`current_block < scoring_end_block`). Refused with
  409 once closed, since no further reveals can arrive and a re-run cannot produce new
  results.

404 if not found, 503 if the current block can't be read to check the window.

After a reset the leader picks the competition up on its next loop tick; no restart
needed.

`POST /v1/competitions/{competition_id}/pause` (requires `Authorization: Bearer <ADMIN_API_KEY>`)
`POST /v1/competitions/{competition_id}/resume` (requires `Authorization: Bearer <ADMIN_API_KEY>`)

Halt the leader's scoring loop for one competition, and start it again — for stopping
a competition mid-flight without losing its state.

Pause stops only the leader's per-tick scoring work (stage 1 and stage 2) for that
competition. Weights already recorded keep distributing, followers are unaffected, and
block-based phases keep advancing — a long pause can run a competition past its
`scoring_end_block`, and the next unpaused tick then finalizes it with whatever was
scored.

Takes effect at the next tick boundary; work already in flight finishes. A candidate
left in `prechecking` keeps that status and resumes from there.

Both routes are idempotent. 404 if not found. Pause returns 409 once a competition has
finished scoring; resume has no such guard. `reset-scoring` clears the flag along with
the rest of the row. `paused_at` is exposed on `GET /v1/state/competitions/{id}`.

## docs/Overview.md
# TPN Subnet Overview (Miner Perspective)

## What you compete on

TPN rewards miners for producing **quantized GGUF versions of a base model** that are small and still accurate. Each competition defines a base model (`model_repo`), a set of benchmarks with minimum scores, and one of two ranking modes:

| `competition_type` | Pass/fail gate | Ranked by |
|---|---|---|
| `benchmark_floor` (default) | Every benchmark ≥ its `min_score` | **Lowest measured RAM** wins |
| `ram_ceiling` | Measured RAM ≤ `max_memory_kb` | **Highest minimum benchmark score** (your weakest benchmark) |

In `ram_ceiling`, a model is only as good as its weakest benchmark — a strong result on one cannot buy rank for a weak result on another.

Competitions are served by the leader validator (`GET /v1/competitions`); `tpn competitions` lists them.

## Competition timeline

Every competition moves through block-based phases:

```
start_block ──OPEN──▶ commit_end_block ──REVEALING──▶ +reveal_grace_blocks ──SCORING──▶ scoring_end_block ──DISTRIBUTING──▶ +distribution_blocks ──COMPLETE
```

- **OPEN** — upload, benchmark, commit.
- **REVEALING** — chain decrypts the timelocked commitments; validators wait out the grace period.
- **SCORING** — the leader verifies, ranks and prechecks submissions.
- **DISTRIBUTING** — validators set weights from the final ranking; emissions flow to winners.
- **COMPLETE** — the competition no longer receives emissions.

## Miner flow

1. **Register** your hotkey on the subnet (`tpn register`).
2. **Upload** your `.gguf` to a **private** HuggingFace repo (`tpn upload`). One repo per submission, exactly one `.gguf` in it. The CLI records repo, filename, **immutable commit SHA** (revision) and the file's **sha256**.
3. **Benchmark** the model yourself on the benchmark service (`tpn benchmark`, paid by you). Every run must be **completed** before the scoring phase starts — a run still in progress then scores 0.0.
4. **Commit** (`tpn commit`): writes a TimeLocked (TLE-encrypted) payload to chain:
   ```json
   {"spec":2,"competition_id":"…","repository":"user/repo","file":"model.gguf",
    "file_sha256":"…","max_memory":<KB>,"huggingface_revision":"<sha>",
    "runs":[{"b":"mmlu","r":"r1234"}, …]}
   ```
   Nobody can read it until the chain auto-decrypts it around `commit_end_block`, so submissions cannot be copied.
5. **Publish** the HF repo (`tpn publish`) before scoring starts. A private repo fails precheck.
6. **Monitor** with `tpn status`, or the leader's `GET /v1/state/competitions/{id}` (per-candidate status and failure reasons).

## Validator side: leader and followers

- One **leader** validator does the real work: reads chain, verifies runs, runs the precheck container, ranks, and publishes results via its API.
- **Followers** download nothing. They poll the leader's final results, compute the same emission weights locally and set weights on chain. When no competition is distributing, every validator copies stake-weighted consensus weights from chain.

## Scoring pipeline (leader)

### Stage 1 — reveal, verify, rank

1. **Scan reveals** from chain `RevealedCommitments`. A reveal is accepted only if it landed within `commit_end_block ± reveal_grace_blocks`, parses as a valid payload, and matches the competition id. **Banned hotkeys are skipped**; unregistered hotkeys are dropped.
2. **Dedup**: if several hotkeys reveal the same `file_sha256`, the **earliest reveal block** wins; the others fail as duplicates. Copying someone's file gains nothing.
3. **Verify runs**: for each competition benchmark, the leader fetches your run id from the benchmark coordinator and accepts it only if:
   - status is `completed`
   - repo matches yours (case-insensitive)
   - it used exactly your committed **revision**
   - your committed **file** is among the run's loaded model files
   - where HF exposes an LFS sha256, it matches your `file_sha256`
   - the run covers that benchmark, the benchmark completed, and it has a score

   Any failure → **that benchmark scores 0.0**. Not fatal by itself, but it will almost certainly fail the floors later. A missing run id also scores 0.0.
4. **Rank** candidates by provisional final score from the verified scores. For `benchmark_floor`, RAM is not yet measured, so this ranking uses your **self-reported** `max_memory`.

### Stage 2 — precheck, in rank order

The leader prechecks **one candidate per loop tick**, top rank first, until `top_n` candidates are scored, candidates run out, or `scoring_end_block` hits. A candidate that fails is marked `failed` and the next one moves up (backfill).

Precheck passes when:
- the HF repo is public
- the committed filename exists at the committed revision
- the **precheck container** (below) accepts the model
- measured RAM is within **±1%** of your reported `max_memory` (`RAM_CHECK_LYING_TOLERANCE`, default 0.01)

After precheck:
- every verified benchmark score must be ≥ its `min_score`
- for `ram_ceiling`: measured RAM must be ≤ `max_memory_kb`

Then the candidate is **scored**:
- `benchmark_floor`: `final_score = −measured_memory_kb` (less RAM ranks higher)
- `ram_ceiling`: `final_score = min(verified benchmark scores)`

### Stage 3 — finalize and set weights

Scored candidates are sorted by `final_score` (descending). Rank *i* receives `emission_distribution[i]` of the competition's pool; ranks past `top_n` get 0.

**Weights only start at `scoring_end_block`**, even if all `top_n` candidates were scored earlier. Finalized results are recorded as soon as scoring completes, but validators only push them on chain once the competition enters the DISTRIBUTING phase, and keep doing so until `scoring_end_block + distribution_blocks`.

While a competition is distributing, each validator:
- sums every distributing competition's shares, scaled by its `emission_weight`
- drops winners no longer registered (their share is not redistributed)
- burns any unallocated weight to uid 0

## The precheck container

A Docker image (`ghcr.io/taofu-labs/tpn-precheck`, built from `shared/validation/precheck.Dockerfile`), public on GHCR. The leader starts one per competition. It runs a small FastAPI service with a pinned CPU build of llama.cpp (`b10020`).

**On startup** it downloads the competition's base model (`model_repo`) once. `/health` reports ready when done.

**`POST /check`** (validator path) downloads your GGUF at the exact committed repo/revision/filename (rejects files > 50 GiB), runs three independent checks, then deletes the file:

1. **Provenance — is this really derived from the base model?**
   - *Tokenizer*: tokenizer type, vocab size and BPE merge count must match exactly; individual entries may differ < 1% (allows added chat-template tokens).
   - *Embedding CKA*: samples 4096 rows of `token_embd.weight` from both models, dequantizes them and computes linear Centered Kernel Alignment. Must be **≥ 0.80**. CKA is invariant to rotation, permutation and scaling, so quantizing or pruning the real base model keeps it high; an unrelated or from-scratch/distilled model falls below the threshold.
   - Fail → `provenance fail`.
2. **RAM measurement**: runs `llama-cli` CPU-only (`-ngl 0`, `-c <ram_check_context_length>` (default 4096), f16 KV cache, `--no-mmap`, generates 1 token) and parses llama.cpp's logged CPU weight and KV-cache buffer sizes. **Measured RAM = weights + KV cache.** Load failure, timeout (600s), OOM kill, or no CPU weight buffer → fail.
3. **sha256** of the downloaded file, compared against your committed `file_sha256`. **A mismatch permanently bans your hotkey** — banned hotkeys are skipped in every future competition.

**`POST /check-local`** (miner self-check) reads a file from a `/data` volume mount and runs the RAM measurement and sha256 (no provenance). Use it to get the exact `max_memory` value before committing:

```bash
docker run -d -p 8080:8080 -v $(pwd):/data ghcr.io/taofu-labs/tpn-precheck
curl -X POST localhost:8080/check-local \
  -H 'content-type: application/json' \
  -d '{"path":"/data/my-model.gguf","context_length":4096}'
# commit ram.ram_bytes / 1024 as max_memory (KB)
```

## Ways to lose (in pipeline order)

| Failure | Consequence |
|---|---|
| Reveal outside grace window / malformed payload / wrong competition id | Not considered |
| Same sha256 as an earlier reveal | Dedup loss |
| Run not completed, or benchmarked a different repo/revision/file | That benchmark = 0.0 |
| Repo private, or file missing at revision | Precheck fail (backfilled) |
| Tokenizer or CKA mismatch with base model | Precheck fail |
| llama-cli can't load the model | Precheck fail |
| Reported `max_memory` off by > 1% from measured RAM | Precheck fail |
| sha256 mismatch | Precheck fail **+ permanent ban** |
| Below a benchmark floor / above the RAM cap | Not scored |
| Ranked below `top_n` | 0 weight |

## Practical tips

- Commit exactly the revision and file you benchmarked; don't push to the repo after benchmarking.
- Measure `max_memory` with `/check-local` at the competition's `ram_check_context_length` — don't guess.
- Make sure every benchmark run has completed before the scoring phase starts.
- Publish the repo before scoring starts.
- In `benchmark_floor`, you're prechecked in order of your *claimed* RAM but paid on *measured* RAM, and a claim off by more than 1% fails outright.
- Emissions only start flowing at `scoring_end_block`, not when your candidate is scored.

### Mocked benchmark runs on localnet

Miners own their run ids in the live flow — the validator only polls them — so
`MockCoordinator` reports any id it did not generate itself as
`unknown run_id`. To drive a full localnet competition with benchmarks mocked
and everything else real, pre-register the ids in a JSON file and point
`MOCK_RUNS_FILE` at it:

```json
{
  "r1001": {
    "repo": "owner/model-GGUF",
    "revision": "<immutable commit sha>",
    "file": "model-q4.gguf",
    "file_sha256": "<64 hex>",
    "benchmark": "mmlu",
    "score": 0.82
  }
}
```

```bash
MOCK_RUNS_FILE=./mock_runs.json TPN_DOTENV_PATH=.env.localnet \
  uv run --package validator python src/validator/main.py
```

`repo`, `revision` and `file` must match what the miner commits, or the run is
rejected exactly as a real mismatch would be. An id absent from the file still
fails, so verification is never weakened. Only `MockCoordinator` reads this —
`BENCHMARK_BACKEND=http` ignores it.

### Commit reveals on a fast-runtime chain

TLE reveals are scheduled in drand rounds (wall-clock), but `scan_reveals`
accepts them by block height, within `reveal_grace_blocks` of
`commit_end_block`. The two only line up while `--block-time` matches the
chain's real rate.

Localnet's fast runtime drifts enough for this to matter: a commit placed far
ahead of `commit_end_block` can auto-decrypt a hundred blocks early and get
discarded, ending the competition with `failed_no_reveals` despite a perfectly
valid payload. Mainnet holds close to 12s, so the default 150-block grace
absorbs it there.

When testing on localnet: measure the real block rate, pass it as
`--block-time`, keep the commit window short, and give the competition a
generous `reveal_grace_blocks`. If reveals are being dropped, the validator
logs the reason at DEBUG:

    reveal_block=1017 outside window for commit_end_block=1133

## Precheck/validation Docker service

`shared/validation/precheck_api.py`'s pure logic (log-parsing regexes,

# TPN Knowledge Base

Reference document for agents acting on behalf of TPN Labs.
Last updated: 2026-10-24

**How to use this file.** Facts in section 11 are unresolved — never state them. Every
performance figure must trace to the public dashboard; if a number is not in this file
and not on the dashboard, do not use it. Section 9 governs all written output.

---

## 1. Identity

**TPN** — True Performance Network. Operating entity: **TPN Labs**.
A **Bittensor subnet (SN65)** that makes large AI models small enough to run on
constrained hardware, and proves they still work.

**Core positioning line:** We make big models small enough to run on constrained
hardware — but powerful enough to be worth running.

**The differentiator, in one line:** The hard part was never making the model smaller.

TPN does not optimize models itself. It runs the market that does.

---

## 2. The problem TPN addresses

Four links in one chain. Agents should present them in this order.

1. **The hardware wall.** The strongest open models need hardware most teams don't
   have. A 70B model at full precision wants roughly 140GB of memory before serving a
   single user. The weights are free; the deployment is not.

2. **Scarcity of the fix.** Compression is a solved science and an unsolved practice.
   Quantization, distillation and pruning all work, but each model needs its own recipe,
   found by trial, by someone who has done it before. Those people are rare and
   expensive.

3. **The measurement failure.** After compressing a model you cannot reliably tell
   whether it still works. Nearly every public benchmark sits in the training data of
   the models it is used to measure, so a score mixes capability with memorisation and
   nobody can separate the two.

4. **What teams do instead.** Over-provision hardware, or rent an API and pay per token
   indefinitely. Both are rational responses to an absence of proof.

**The hinge:** What holds back local and on-device AI isn't that models can't be made
smaller. It's that nobody can prove the small one is still good.

---

## 3. The mechanism

### 3.1 Specification in, verified model out

A requirement enters as hard numbers: a **memory ceiling** the model must fit under and
a **quality floor** it must clear. Both are machine-checkable. The two-axis framing
(ceiling and floor) is core brand language.

### 3.2 Open competition

The specification is published as an open competition. Independent teams worldwide
attempt it in parallel, each with their own methods. Best result wins.

Participants are paid by Bittensor protocol emissions, not by TPN and not by the
customer. **Running one more competition costs TPN close to nothing.** Capacity scales
with participants, not headcount. This is the central economic claim.

### 3.3 Sealed scoring

TPN generates its own evaluation sets rather than using public ones, keeps them sealed,
and publishes a cryptographic hash of each set before any model is submitted.
Competitors cannot train against a test they have never seen; the hash proves afterwards
that the test wasn't changed to suit a result.

### 3.4 What the customer receives

Open weights, the scores, the exact model revision, and a public run record anyone can
re-check. The model and the proof arrive together.

### 3.5 Commit / reveal

Competitions use a commit/reveal window. Submissions are committed on-chain, then
revealed and scored.

---

## 4. fluid_knowledge — the benchmark

The private, generated benchmark used to score competitions.

- Generated in-house, never published.
- Organised in **sealed epochs**, each committed by hash before submissions open.
- Approximately **1,400 items**.
- Graded 1–10.
- Organised across **seven concerns**:
  1. Material world
  2. Living systems
  3. Minds & action
  4. Collective life
  5. Constructed systems
  6. Meaning & expression
  7. Formal relations

**Why the seven concerns matter rhetorically:** a model tuned to game one subject area
spikes in one column. Uniform improvement across all seven indicates a real capability
gain, not a scoring artefact. Use this argument whenever presenting a result.

**The moat claim:** Every public benchmark gets less useful the moment it's published.
Ours get more valuable the longer we keep running them. A competitor starting now begins
at epoch one.

**Known risk, internal only — do not publish:** miners can in principle hill-climb
against fluid_knowledge through repeated Bench queries. Leadership has chosen not to
publish this.

2. **Deployments where the cloud isn't an option.** Edge, robotics, factory floors,

3. **Anyone who has to trust a number.** Procurement, auditors, regulators. A score on a

Energy (smaller model, less energy per token) and sovereignty (local execution keeps

## 9. Voice and writing rules

### 9.1 Tone

Plain and direct. State the fact and stop. Short sentences, concrete nouns, real
numbers. Confident without selling — show evidence rather than making claims. Technical
where it earns the reader something, never technical as decoration. If something is
uncertain, say so.

**Do not address the reader as "you" in announcements.**

### 9.2 Banned constructions

- "Not just X, but Y" and every reversal of that shape
- Three-item fragment lists for rhythm ("Faster. Smaller. Better.")
- A colon used to set up a dramatic phrase
- Em dashes used for drama
- Sentences telling the reader what matters ("here's why this matters", "and that's the
  important part", "this changes everything")

### 9.3 Banned words

revolutionary, game-changing, unlock, unleash, seamless, cutting-edge, leverage (verb),
empower, robust, elevate, supercharge, transform, journey, landscape, delve, moreover,

# Subnet Game Theory: Verifiable Private Benchmarks

## TPN v0.2: Fluid Bench Upgrade

We've run four competitions so far, and each one has revealed that the hardest problem in what TPN does is measuring what do models keep when they get compressed.

Every round has taught us more about how to measure that well, and TPN v0.2 is where all of it comes together.

Fluid Bench is TPN's first major upgrade, It ships with competition 5 and changes how submissions are scored from the ground up.

## Removing "trust" from the equation

Fluid_knowledge is a new type of benchmark we introduced as part of the Fluid Bench upgrade; one that doesn't test absolute intelligence, but tests relative intelligence in a context where we (or any party) cannot rely on trust alone in the people who optimise LLMs.

It is available now at the TPN benchmarker: https://bench.trueperformancenetwork.com/dashboard

Fluid_knowledge answers the question "how do you benchmark models if those creating them have an incentive to cheat?"

The game theory behind Bittensor subnets could be summarized as:

- The owner wants miners to provide a service, and the miners do not trust the owner;

- The miners want to get rewards with the least effort possible, and the owner does not trust the miner.

In the case of TPN (Subnet 65):

- We want miners to optimise open source LLMs to fit on smaller hardware while maintaining intelligence;

- The miners compete with each other, and have an incentive to take shortcuts.

A SN65 competition usually specifies something like "the winner is the smallest model that can beat benchmark X at 80%". The problem is that the benchmarks we have been using thus far were public, meaning miners can overfit on them (meaning the model gets REALLY good at passing the test and dumb at everything else). A possible solution would be private benchmarks, but miners do not trust subnets owners to be honest, so this is out of the question.

Fluid bench is the outcome to one question: "can we generate synthetic benchmarks that test whether an LLM was finetuned in an unhelpful way?"

With this question in mind, we designed the following approach:

- We have a benchmark template, think along the lines of "Section 1 tests biology knowledge, section 2 tests math knowledge, etc"

- We use a committee of frontier models to randomly sample questions in the section domains

- While we use the benchmark, the questions are secret but their hash is public

- Once the benchmark is used for a while, we publish the questions and miners can verify that we were honest by checking the hash

- We then regenerate the benchmark based on the template, and we publish the hash of the new iteration

Usually, this approach makes no sense.

Every generation from the benchmark template will be different. The first time we run it, the biology question might be about elephants, and the second time about microbes. It is also an approach that will probably never work to benchmark frontier models, as the questions themselves are biased on the knowledge the frontier models have.

But for us, that does not matter.

The goal of Fluid Bench is not to see "how good is this model", the goal of fluid bench is to see "did this model overfit on benchmarks".

This is what we use the fluid_knowledge benchmark for:

- We benchmark a base model with fluid_knowledge

- The miners submit their optimised models, and we check the loss this model has on fluid_knowledge

Fluid_knowledge does not answer "is this model smart", it answers the "is this model dumber than the other model?" question.

Answers are graded on a scale of 1 to 10 rather than marked right or wrong, so a model that half knows something scores differently from one that doesn't know it at all. 

This upgrade and related benchmark are a byproduct of a relationship between parties that need to interact with one another in a decentralized environment, where trust can't be part of the structural equation; thus eliminating the need to operate on trust altogether.

fluid_knowledge is not restricted to competitions. It is available to anyone running a model through TPN Bench, which makes it useful well beyond Subnet 65, every public benchmark carries some risk that a model has already seen it, and under that lense, fluid_knowledge carries none.

## Benchmark first: scores that can be verified

Until now, scoring worked in two steps. Miners reported their benchmark scores alongside their model, and the validator then re ran those benchmarks to confirm "the math is mathing".  It worked, but every submission was effectively benchmarked twice, and scoring could only move as fast as the re runs.

In TPN v0.2. Miners now run the benchmark suite for a competition themselves through TPN Bench before they submit. Along with their model, they submit the run ID for each benchmark. The validator checks those IDs directly against the benchmarker's back end, confirming that each run is real, was performed on the submitted model, and produced the actual score the miner reported.

Thus self reported score claims become records. A score that matches a verified run is true by default; one that doesn't, doesn't count. And with no re runs needed, the scoring phase gets leaner.

It also means the network and the public product now run on the same foundation. The TPN Bench that miners use to prove their results is the same one open to any developer, lab or team benchmarking a model.

## Competition 5

We will soon start the TPN-005 competition where we'll put Fluid Bench to the test.

It is scored on fluid_knowledge alone. No public benchmark is in the mix at all this round, so nothing in the scoring can be studied in advance.

Some details may still be refined before the competition opens, and the docs will stay current as they are.

## The standard stays the same

The goal of Subnet 65 remains to output the highest quality optimized models the network can produce. v0.2 makes sure the scores that decide them are ones everyone can trust, miners included.

# TPN-005 Model Case Study

## TPN-005: optimizing an 8B model for a constrained chat interface environment

A TPN Labs case study | October 2026

## Abstract

TPN fifth competition asked the network for a purpose built LLM that could fit a chat interface and performs well on general knowledge, the capability such interface depends on most.

Miners complied to the request, tuning the base model toward the requested capability. 

All three finalists cleared the base reference; the base model can’t run in this environment, whereas the winners can. 

Scoring ran entirely on fluid_knowledge, a private benchmark generated by TPN, which is not published before the competition, so no submission could have been trained on its contents.

Every result in this study is tied to a sealed epoch, an immutable model revision, and a public evidence record.

## The ask

A model that runs on hardware someone already owns has to do two things at once. It has to be the right size to run on the machine it is given, and it has to stay good enough to be worth running.

We set both limits upfront and for TPN-005 we asked the network to find a model that satisfies them.

Memory:
The size limit was 11GiB of memory, which is what a model has to fit inside to run on an ordinary machine (in this case a chat interface where the memory available is fixed and cannot be negotiated).

The 11GiB limit is memory used while the model is running, not the size of the file on disk. This difference is key, because a running model also holds the conversation in memory, and the 11GiB memory had to hold the model and everything said to it.

Capabilities:
The capability requirement was general knowledge, measured on a benchmark nobody could prepare for in advance. A chat interface is a general purpose tool, and the thing users notice first is whether the model knows things.

Base model: Ministral-3-8B-Uncensored (GGUF F16, 16.99GB)

## Results

All three finalists came in at roughly 7.2GB against a 16.99GB reference, and all three scored above it.

The winning model measured 10.98GiB of RAM at inference against the 11GiB ceiling. The constraint was met just under the requested value, which is what a well specified ceiling should produce.

The winning submission, TPN-005 K11, is a ~7GB GGUF scoring 73.93% on fluid_knowledge against the 16.99GB F16 base model's 66.57%.

That is 57.4% smaller and 7.36 percentage points stronger on the capability specified.

Addressing the "gain" over base model.

Compression alone generally cannot raise a benchmark score, as quantization only discards information. The finalists score higher because they were not only compressed but tuned toward the capability the competition specified (general knowledge).

The winning artifact is named tpn005-sft8-ME.gguf, and its profile is consistent with supervised fine tuning directed at the scored concerns.

Specification driven optimization.

The network was told what to optimize for, and it optimized for that.

No quantization claim is inferred from these figures, the comparison is between the published F16 reference and the submitted artifacts, measured on the same sealed epoch under identical settings.

## Reading the concern profile

The overall score is supported by seven concern scores. Breaking the result apart shows that the improvement was not evenly distributed.

A main pattern stands out: Meaning & expression moved furthest.

The base model's weakest concern at 60.31% became one of the stronger ones at 74.23% in K11, a gain of 13.92 points. Constructed systems follows at +11.98 and Collective life at +10.71. These are knowledge recall concerns, and they responded most to optimization.

That asymmetry is useful to know as the concern profile shows where this model is strong and where it is not. For a chat interface built on general knowledge, the gains landed where they were needed, whereas a task leaning on formal or logical reasoning would want a different target.

## What this demonstrates

TPN-005 set a specification and the network met it.

The specification had two parts, a hard memory ceiling and a named capability, and the result satisfies both: a 7.24GB artifact running in 10.98GiB, scoring 73.93% on the capability that was asked for.

That is the mechanism working as designed. A competition does not ask participants to make a model generically better, which is an unbounded problem with no finish line. It asks for a model that fits a stated constraint and performs on a stated axis, those are answerable questions that TPN-005 answered successfully.

The practical outcome is a model suited to its intended environment.

An 8B that runs inside 11GiB with a full context window, and holds up on general knowledge, is a model that can sit behind a chat interface on hardware people already own, which is a direction the industry is moving toward, even as many models remain too large to run this way.

## Why fluid_knowledge

The weakness of a public benchmark is structural, as its questions are public.

MMLU, HellaSwag and ARC have been on the internet for years, which means they sit in the training data of nearly every model released since. A high score on them is ambiguous, because it could either reflect that the model is very good, or that the model was trained specifically to pass these tests while being "dumb" at everything else.

That ambiguity is tolerable when measuring a model once. It is not tolerable when running a competition, where participants are rewarded for the score itself.

fluid_knowledge's set of questions are generated from a benchmark template by a committee of frontier models, frozen into a versioned epoch, and never published while that epoch is in use.

Participants receive a score and nothing else. The epoch's hash is published while it is sealed, and the questions are released afterwards, so anyone can verify that the set used was the set committed to.

The epoch used for TPN-005 was 000001-r7. Each run evaluated 1,400 items, scored across seven concerns rather than collapsed into a single opaque number.

## Method

TPN-005 ran as an open competition on Subnet 65. Participants received the base model, the memory ceiling and the benchmark, and were free to reach the target however they chose. Submissions are weights rather than methods. The network specifies the destination and leaves the route open.

Scoring used benchmark first verification, introduced in TPN v0.2. Rather than re running every submission, participants benchmark their own models through TPN Bench and submit the resulting run IDs alongside the weights. Each ID is then checked against the benchmarker's records, confirming the run took place, ran on the submitted model, and produced the reported score. A score that matches a verified run is true by construction; one that does not is not counted.
